# Base Effect Analogy: referencing a guideline from another Technique/Form

**Todo items:** 25 (unblocks, in a follow-up, *Restore the Moved Image*,
*Dispel the Phantom Image*, *The Invisible Eye Revealed*, *Lay to Rest the
Haunting Spirit*)

**Status:** designed 2026-08-16

**Rulebook:** `Ars-Magica-Open-License/reviewed/Ars Magica - Definitive
Edition (Core Rules).md`. Line references in this document are to that file.

---

## Problem

Four published spells share a mechanic the rulebook only formalizes, with a
magnitude offset, at the Vim level — Perdo Vim's "dispel"/"reduce Might"
guidelines, Rego Vim's "sustain or suppress" guideline — and never tabulates
per-Form. Their own Technique/Form's guideline table prints either no
matching row at all, or the wrong one (a ward). Building a per-Form catalog
row from each spell's own prose was already tried once for two close
relatives (`peme-G`, `inco-gen`) and reverted: it invents rulebook content
the printed table doesn't contain, and a test
(`test_general_entries_match_the_rulebook_bullet_for_bullet`) now holds the
catalog to the rulebook's own General bullets, art by art, in both
directions, permanently.

What none of that prior work considered: the way real Ars Magica spell
design actually handles this. A magus inventing a spell whose effect has no
guideline in their own Form routinely designs it **by analogy** to a
guideline that exists elsewhere — most often Vim, which is where the
game's generalized versions of Perdo/Rego mechanics already live. This is
not inventing content; it is citing real, already-printed content and
explicitly recording that it's being applied outside its own Form.

The catalog has no way to represent this today. `Spell` and `SpellTemplate`
each hold exactly one `baseEffectId`, and nothing anywhere checks — or
permits — that id's own Technique/Form to differ from the spell's. Worse:
`ResolvedSpell.technique`/`.form` and `ResolvedTemplate.technique`/`.form`
are *derived* from the resolved `BaseEffect`, not stored on the record at
all. A spell built on a borrowed guideline would silently display under the
**borrowed** Technique/Form — *Restore the Moved Image* would show as Rego
**Vim**, not Rego **Imaginem** — which is wrong in a way that matters:
Magic Resistance is determined by a spell's own Form, not one it happens to
reference (Requisites, Core Rules: *"The defender's Magic Resistance is
determined by the spell's primary Form, not that listed as a
requisite..."*).

## Explicitly not in scope

**Actually unblocking the four spells that motivated this.** Each still
needs its own per-spell derivation work once this capability exists —
tracing through *Restore the Moved Image* during design surfaced a real
complication: its printed design line shows zero Range/Duration/Target
tokens (`"(Base effect)"`) despite a non-Personal stat line (Voice range),
which is exactly the arithmetic mismatch that trips assertion 6
(`ReferenceOracleTest`) today. Borrowing a Vim guideline doesn't
automatically resolve that; each spell needs its own reference R/D/T (and
possibly its own, lower, magnitude offset — the Form-level flavor-text
versions of this mechanic never carry the Vim-level offset) worked out by
hand and checked the same way every other entry in `NUMBERED_OVERRIDES` is.
That is a follow-up to item 25, not part of this plan.

**Creation-screen UI for picking a cross-Form base effect.** The screen
currently picks Technique+Form first and filters the base-effect list to
match; relaxing that is real design work of its own (as the user who
proposed this feature already flagged: "surfacing that in the UI will be
harder"). This plan makes the data model and import pipeline support
analogy; a user cannot yet create one interactively.

**Any enum-style validation of `technique`/`form` values.** Plain strings,
matching `BaseEffect.technique`/`.form` and `ExceptionSpell.technique`/
`.form`'s existing convention — no new validation beyond what already
exists for those fields.

**Catalog changes.** `base_effects.json` is untouched. Analogy only
references base effects that already exist, printed, in the rulebook.

## Backwards compatibility is not a goal

Eruditus is a prototype with no users. `technique`/`form` become required
fields on `Spell` and `SpellTemplate`; every entry in the committed assets
is regenerated by the importer in one pass. No migration path is designed
and none should be added — a local database missing the new fields is
dropped and rebuilt, the same discipline every prior model change in this
project has used.

## Design

### 1. `Spell` and `SpellTemplate` gain their own Technique/Form

```dart
class Spell {
  // ... existing fields ...
  final String technique;
  final String form;
  /// Non-null only when [technique]/[form] differ from the resolved base
  /// effect's own technique/form -- the citation-backed reason a human
  /// chose to apply that guideline outside its own Form. Null whenever they
  /// match; enforced by `validateSpellAgainstCatalog`'s new check.
  final String? analogyRationale;
}
```

Identically on `SpellTemplate`. Both become **required, non-nullable**
fields (`analogyRationale` stays nullable, as designed) — this reverses
`Spell`'s own documented principle ("this record deliberately holds no copy
of any catalog data — no base level, magnitude, technique or form"), and
that reversal is deliberate: technique/form were always safe to derive
*only* because nothing could make them disagree with the base effect. Once
a spell can legitimately reference a base effect outside its own Form, that
assumption is false, and there is no way to recover the spell's *real*
Technique/Form except by storing it.

`toMap()`/`fromMap()` follow the existing pattern exactly — `requireField`
for `technique`/`form`, a plain nullable read for `analogyRationale`.

### 2. Validation: `validateSpellAgainstCatalog` gains an 8th check

```dart
// 8. A spell's own Technique/Form is now stored, not derived, so it can
//    legitimately differ from its base effect's -- but only when that
//    difference is explained. Symmetric: an unexplained mismatch is a data
//    bug (the record and its guideline silently disagree); an explanation
//    attached to a spell that doesn't actually differ is meaningless
//    decoration, the same class of bug check 2 catches for a stray
//    chosenBaseLevel.
final isAnalogy = technique != effect.technique || form != effect.form;
if (isAnalogy && (analogyRationale == null || analogyRationale.trim().isEmpty)) {
  problems.add(
    "Technique/Form differs from the base effect's own -- "
    'an analogyRationale is required to explain why',
  );
} else if (!isAnalogy && analogyRationale != null) {
  problems.add(
    'analogyRationale is set but Technique/Form already matches the base '
    "effect's own -- remove it",
  );
}
```

Placed after check 7, and — unlike checks 1, 2 and 6 — **not** wrapped in
`if (!isTemplate)`: a template needs its own correctly-recorded
Technique/Form exactly as much as a spell does, so this runs unconditionally
for both, the same as checks 3, 5 and 7.

Two new required parameters on the function: `required String technique,
required String form, required String? analogyRationale`. Every existing
call site (`ResolvedSpell.problems`, `SpellEngine.validateSpellDraft`, and
`published_spell_import_test.dart`'s assertion 7, for both the spell and
template loops) passes the record's own three new values through — a
mechanical update at each site, not a design decision, since the record
already carries them.

### 3. `ResolvedSpell`/`ResolvedTemplate`: read the stored field, not the base effect

```dart
// Stored on the record, not derived: a spell's own Technique/Form may now
// legitimately differ from its base effect's (see analogyRationale) --
// deriving from the base effect would silently display the wrong one.
@override
String? get technique => record.technique;
@override
String? get form => record.form;
```

Replaces the `baseEffect?.technique`/`.form` getters (and their now-inverted
doc comments) on both classes identically. This is the fix for the
wrong-Form-in-the-UI problem `SpellCard` and everywhere else in the app
that reads `LibraryEntry.technique`/`.form` inherits automatically — no
further UI change needed for *correct display*, only for *authoring* one
interactively (out of scope, above).

### 4. `SpellDraft` → `Spell`: thread the already-existing fields through

`SpellDraft.technique`/`.form` already exist (used today only to filter the
base-effect picker) but are never passed into the `Spell` `toSpell()`
constructs. They now are:

```dart
Spell toSpell({required String name, required PublicationSource source}) {
  final missingFields = <String>[
    if (baseEffect == null) 'baseEffect',
    if (technique == null) 'technique',
    if (form == null) 'form',
    if (range == null) 'range',
    // ... existing checks ...
  ];
  // ...
  return Spell(
    // ... existing fields ...
    technique: technique!,
    form: form!,
    analogyRationale: null, // the creation screen cannot produce one yet
  );
}
```

`SpellDraft` itself gains no new field — `analogyRationale` has no UI path
to populate in this phase, so `toSpell()` always passes `null`, and every
user-created spell's `technique`/`form` continue to match its base effect's
own exactly, the same as today (the picker still filters to matching base
effects only). `SpellTemplate` needs no equivalent draft-conversion path:
it has no user-creation flow at all (see `lib/models/spell_template.dart`
— published-only, no `fromDraft`).

### 5. Python importer: emit the spell's own Technique/Form always

```python
def build_spell(
    block,
    base_effect_id: str,
    catalog: catalog_module.Catalog,
    design: designline.Design,
    realm_by_spell_id: dict[str, str] | None = None,
    chosen_base_level: int | None = None,
    override_modifiers: dict[str, list[str]] | None = None,
    extra_adjustment: tuple[int, str] | None = None,
    analogy_rationale: str | None = None,
) -> dict:
    ...
    spell = {
        "id": ...,
        "name": block.name,
        "technique": block.technique,
        "form": block.form,
        ...
    }
    ...
    if analogy_rationale is not None:
        spell["analogyRationale"] = analogy_rationale
```

Identically on `build_template`. `block.technique`/`block.form` are always
available — every `SpellBlock` already carries them, used today only to
build the slug id — so this is a pure addition, not a new derivation.
`analogy_rationale` defaults to `None` and every current call site passes
none: no published spell uses this yet (see "Explicitly not in scope"),
so `NUMBERED_OVERRIDES` gains no new entries in this plan. The parameter
exists so a future entry can supply one, exactly the way
`extra_adjustment` was added ahead of *Conjuration of the Indubitable
Cold*'s specific fix in the same session.

**Regeneration.** Every one of the 325 spells and 24 templates already
carries a real `technique`/`form` on its parsed `SpellBlock`; adding the
two keys to every emitted entry and re-running `--write` is a pure,
mechanical regeneration — no spell's `baseEffectId`, level, or any other
field changes, and assertion 1/6 are unaffected (this touches only two new
keys, not the arithmetic).

## Testing

- **Dart model tests** (`test/models/spell_test.dart`,
  `spell_template_test.dart`): construction with matching Technique/Form and
  no rationale (existing shape, still valid); construction with a mismatch
  and a rationale (valid); construction with a mismatch and no rationale,
  and construction with a rationale but no mismatch (both invalid, via
  `validateSpellAgainstCatalog`, not the constructor — the constructor
  cannot see the base effect, same as every other catalog-dependent check).
  `toMap`/`fromMap` round-trip including `analogyRationale`.
- **`validateSpellAgainstCatalog` tests**: the new check's four states
  (match+null, mismatch+rationale, mismatch+null, match+rationale) proven
  directly, not just through a fixture spell.
- **`ResolvedSpell`/`ResolvedTemplate` tests**: `technique`/`form` read the
  record, confirmed with a fixture whose base effect deliberately disagrees
  (proving the derivation actually changed, not just that the common case
  still works).
- **Python `test_emit.py`**: `build_spell`/`build_template` emit `technique`/
  `form` matching the block; `analogyRationale` present only when passed.
- **Python `test_extract.py`**: regeneration byte-for-byte, same discipline
  as every other asset change this session.
- **`published_spell_import_test.dart` assertion 7**: updated call sites are
  the regression guard that every one of the 325 real spells and 24 real
  templates has `technique`/`form` matching its base effect and no stray
  `analogyRationale` — this is the free, whole-corpus check that the
  regeneration didn't introduce a spurious mismatch anywhere.
- **Full three-suite verification** (Python, Flutter, Windows integration)
  after the asset regeneration, matching every other change this session.
